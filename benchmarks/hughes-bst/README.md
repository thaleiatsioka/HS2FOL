# Hughes, "How to Specify It!": binary search trees

Source: John Hughes, *How to Specify It! A Guide to Writing Properties of
Pure Functions*, TFP 2019; code from
<https://github.com/rjmh/how-to-specify-it> (MIT licence, see
`LICENCE-how-to-specify-it.txt`).

| file | contents |
|---|---|
| `BST.hs` | the correct implementation (unchanged from the repository) |
| `BST1.hs` … `BST8.hs` | the eight buggy versions (unchanged) |
| `Nat.hs` | Peano numbers, used as keys and values |
| `template/BSTSpec.template.hs` | the properties of `BSTSpec.hs`, adapted (see below) |
| `BSTSpec0.hs` … `BSTSpec8.hs` | generated by `generate.sh`: the properties against `BST`, `BST1`, …, `BST8` |

The benchmarks are the 40 properties in each `BSTSpecN.hs` (9 × 40 = 360
problems).

## The bugs (Table 1 of the paper)

| | bug |
|---|---|
| 1 | `insert` discards the existing tree, returning a single-node tree |
| 2 | `insert` fails to recognise and update an existing key, inserting a duplicate entry instead |
| 3 | `insert` fails to update an existing key, leaving the tree unchanged |
| 4 | `delete` fails to rebuild the tree above the key being deleted |
| 5 | key comparisons reversed in `delete`; only works correctly at the root |
| 6 | `union` wrongly assumes that all keys in the first argument precede those in the second |
| 7 | `union` wrongly assumes that if the key at the root of t is smaller than the key at the root of t', then all keys in t are smaller than that key |
| 8 | `union` works, except that when both trees contain the same key the left argument does not always take priority |

## Adaptations of the properties

The implementations are used as they are. The property file differs from
`BSTSpec.hs` as follows:

* **Keys and values are `Nat`**, not `Int`/`Integer`. hs2fol keeps `Int`
  abstract, so with `Int` keys every key comparison would be uninterpreted and
  nothing could be found.
* **Trees are generated as in the paper.** Hughes' `Arbitrary` instance builds
  every tree as `foldr (uncurry insert) nil kvs`. A property argument
  `t :: Tree` is therefore replaced by `kvs :: [(Key, Val)]` with
  `t = tree kvs`. Without this the prover could choose *invalid* trees (which
  QuickCheck never generates) and report spurious counterexamples. Note that
  with a buggy `insert`, `tree` uses the buggy `insert`, exactly as in the
  paper.
* `Data.List.insert`, `sort`, `unionBy ((==) `on` fst)` and
  `Control.Applicative.<|>` are defined locally with the same meaning, since
  hs2fol does not support qualified names.
* **Left out:** `prop_SizeInsert` (`Int` arithmetic), `prop_ShrinkValid` (uses
  `shrink`), and the `Equivs` congruence properties (their generator uses
  `shuffle`).

`BSTSpec0` (correct implementation) is the control group. A confirmed
counterexample there means the property itself is false for the correct
code. `prop_UnionUnionAssoc` compares trees structurally (`===`), so it may
fail even for the correct `union`. A witness that is *not* confirmed means a
bug in hs2fol.

## Checking with QuickCheck

The files are ordinary Haskell:

```
ghci -ibenchmarks/hughes-bst benchmarks/hughes-bst/BSTSpec3.hs
> quickCheck prop_InsertPost
```
